From scene tree to shader

The builder keeps a scene as a tree: groups, shapes, their sizes and joins. The kernels need the scene's distance as WGSL code (chapter 2's SDF, every shape and join of chapter 3). Turning one into the other is code generation, and how it is done decides what an edit costs: a value written, or the whole program compiled again, seconds each. This chapter is ShadyTracer's three answers, code with uniforms, baked constants, and the scene as data, and why a kernel's size, not its text, decides how long it takes to compile.

1What changes the text

A small flat scene of one group: a block, a ball joined to it and a hole cut in it, blended by k (chapter 3). Written as ShadyTracer's code generator writes a scene: the structure as code, a line for each shape and join, and every number a uniform read, UB.pos_c, the ball's position. That text is compiled into every kernel that needs the scene (chapter 21). One program compiled so far.

Drag the ball (or the hole, or move the blend slider). The text is the same, so nothing compiles: the new position is written into the uniform buffer, and the next frame uses it. In the builder this is a "live" change, and why dragging a shape is smooth.

Add a ball. That is new code, two new lines (marked), so the program is compiled again. In ShadyTracer a structural edit, a shape added, moved to another group or given another material, took 3.7 to 23 seconds uncached on the user's Ampere card for the bundled scenes (section 5).

Baked: the same code, every uniform turned into a constant by the engine's own bake (this page runs it). The compiler can fold constants into the arithmetic, and a shape not turned or scaled loses its matrix products, so the kernels run faster (section 5). But now every change is new text: move the ball and it compiles again. ShadyTracer bakes in the background once the edits stand still, and goes back to the code with uniforms while they move.

As data: one text for every such scene, a loop over records, one a shape: its kind, its join, its numbers. Adding the ball added a record and no line; nothing compiled. The price is the loop: reading records costs more a step than numbers written into the code (section 5).

2A kernel's size is its copies

A kernel calls the scene's distance in several places: the march, the normal's differences (four calls, chapter 4), the material lookup. The compilers behind WebGPU inline nearly every call: a function called from four places is compiled four times. So what a compile costs follows the kernel's size with every call written out, not its text. Here, a kernel with a scene of 40 objects written as the code generator writes them, called once: 6,794 characters inlined.

Called from four places: the text barely grows, the inlined size is four times, 27,020. The curve is the engine's own model of compile time, fitted on the user's GTX 1080 Ti over 16 builds: 15.2 ms for every 1000 inlined characters at about 151,000, and growing faster than the size, as its 1.37th power (dashed: the same rate held linear).

400 objects, four places: 273,500 characters inlined, about 5 seconds predicted. The lens assembly copied 32 times, which the linear rate put at 97 seconds and the fitted model at 6.5 minutes, was still compiling after ten minutes, which is one reason the scene as data exists. The other lever is fewer copies: section 6 has the six copies one function held.

4Tricks and trade-offs

    
Each is stamped with how it is known; point at a stamp to see what it means.

    

      
Baked runs faster, mostly. On the user's Pascal card, 1280 × 720 (0.28.0), codegen against
        baked: the optics bench's march 189.7 to 61.2 ms a sample (−68%), its whole GPU time 297.4 to 109.1; baked faster
        on seven of eight scenes. The exception, the Noise library, was 5% slower to march, not explained. Compiling baked
        was no slower anywhere: the optics bench's scene kernels 8,456 to 4,643 ms (roadmap/ARCHITECTURE.md,
        the bake run).

    

    

      
Data costs a step. The march as data against codegen, same card: 4.2, 3.9 and 3.1 times as long
        on three small scenes, 8.9 and 9.4 on the demo and the Menger cubes, and 0.83 on the optics bench, the biggest,
        where data was faster (the same document, before step 5). So the scene as data is a developer switch, off by
        default, and the builder edits with code and renders baked.

    

    

      
A structural edit. A whole compile: 3.7 to 23 s uncached on the Ampere for the bundled scenes
        of 2 to 14 objects (docs/PERFORMANCE.md, run 4).

    

    

      
One text whatever the size. The records are copied into a uniform buffer of 4096 vec4s, the
        64 KiB every device allows (chapter 21): room for 585 records; any past that are read from the storage buffer
        where they also are, so a scene of any size is the same text (scenedata.js, the room).

        patterned material, so a lookup with six such materials held six more copies of the scene at every place it was
        called, and the Noise library took over a minute to compile

        noUnroll (wavefront.js, the march kernel; chapter 27).
