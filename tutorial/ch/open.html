Part IX · Build your own · Chapter 33

Open problems

The last chapter is what nobody knows yet. ShadyTracer's own documents keep a careful account of it: checks built and never run on a graphics card, one run once and still open, numbers measured on a card that nobody has explained, fixes designed and not built, and limits the renderer has and says so. And writing this tutorial found comments in the code that say something the code, or its own numbers, does not. Each is a place to start. The board below holds them all, every card quoting its document, and the tutorial's test checks each quote against today's files, so the board must change when a check is run or a comment fixed.

1The board

Every open item, a card each, in columns by kind; point at a card for its source, its words and the chapter that teaches what it is about. The largest group is the first, and the reason is where the code is written. Much of ShadyTracer is written by an AI assistant working in a container: a computer hired for the job, reached over the internet, whose graphics card is a software imitation that cannot run the page (the repository's notes for the assistant say so). The numbers need a real card (chapter 0). A check of the picture is a row of the bench (lib/pathtracer/tests.js, listed in docs/TESTING.md): it tells something only once someone with a real card presses it and pastes the numbers back. Until then it is code that has never run.

The rows built and never pressed. Take the first: is each error bar the real noise? Every pixel reports an error bar (chapter 12); the row renders a floor whose every pixel should read the same, and compares how far neighbouring pixels really differ with what their error bars claim. A pass reads 1; a failure says every error bar in the program is too wide or too narrow. Chapter 29's figures show what it would see, but nobody has pressed it. The others ask whether the illuminance view reads the lux a surface really gets (chapter 5), whether the surface tolerance follows a scene's size (chapter 30), whether the far field gives a known source's curve (chapter 31), whether the photon map adds exactly its share (chapter 19). Four ask only what something costs, not whether it is right: the frame buffer's compare-and-swap (chapter 23), the occlusion queue (chapter 22), an iteration, the Quality presets. And one row has been pressed once and is still open: an earlier test read light sampling 76% brighter with a sun twenty times the real one, in a scene with a glowing object of its own, which light sampling does not cover; the row built to tell whether the sun's disc or the sky is wrong was pressed once, and its answer is not recorded (chapter 14).

Measured on a real card, and nobody yet knows why. Take the furnace (chapter 29): an object in a white sky of brightness 1, which a surface that loses no light must read as exactly 1. Rough glass loses a little, because light that would bounce between the tiny facets of its rough surface is not followed: on the Pascal card it read 0.9587, and a separate program on the processor, with the same model of the surface and no code shared with the renderer, found the same loss (5.3% on the sphere, which fills 0.78 of the picture: 4.1% over the whole). So 0.9587 is explained. Then on the Ampere card it read 0.9872 in one set of runs and 0.9440 in every run since, its own sampling unchanged and a narrower picture accounting for at most a quarter of the difference: "Not explained yet." The same question is on the other cards: the Noise library's compile, about 4 s in one profile and 21 to 23 s in the benchmark on the same card (chapter 27); the same kernels reading 184.7 to 255.5 ms from run to run, so that a comparison across runs is "good to about ±20%", the drift (chapter 25); one scene, re-authored in metres, 10% faster than its neighbours on the very same kernel text. These are the most valuable cards: each is a number that should be one thing and is another.

Designed and agreed, never built. Take the first: a tolerance for each pixel. Today one surface tolerance serves a whole scene (chapter 30), so in a large scene a small object close to the camera gets one too coarse for it; the user asked for "different eps for different pixels", it was agreed, and the engine's move to metres was built first to make it possible. The others: a probe for the thin air gap two slabs of glass leave; a compensation for the light rough glass loses; shadow rays weighed through frosted glass; light faces that reflect; a photon map for dust. Each design is written down where the card's source says.

Limits the documents state plainly. A bug, as this chapter uses the word, is the program doing what nobody meant, unknown until someone finds it: section 6 of chapter 32 tells two. A limit is known, measured or bounded, and says where the picture cannot be trusted: the surface tolerance making a small lamp too bright is one (chapter 30 measures it). The others: a light reached only through glass, left to chance (chapter 18); the biases the wavefront keeps (chapter 22); light's polarisation, which no face keeps track of (chapter 10).

Comments and documents that say what the code, or their own numbers, do not, found while writing these chapters. Take the first: the comment on aiming at the sun says it is "a cone of about 0.03 steradian", but that was an old sun drawn 21 times too wide, covering 441 times the sky; the real sun is 0.000067 steradian (chapter 14). The others: a comment's arithmetic that its own constants do not give; a speed-up claimed "on every scene" from one; line numbers the code has moved past; the plan calling the camera's depth of field "not built" while further down it says the lens was built in 0.43.0. Each chapter that found one says so beside the quote. None is changed here: whether to fix each is the code's owner's call.

2How one gets closed

The way every number that decided anything here was made (chapter 25): a row of the bench, run on a real card by the person who has one, its result pasted back with the version line that names the build. Then the row's status in docs/TESTING.md changes, and this board with it. A row is closed when its answer is known, whether it passes or not: a check that fails has told something, and a check never run has told nothing.

When that happens, or a comment is fixed, a card's quote no longer matches its file. The tutorial's test then fails, and since the repository runs that test on every proposed change (its CI), the change cannot pass until the board is brought up to date in the same change. That is how the board stays true without anyone remembering to update it.

And the rules for writing the answer down are the ones this tutorial has stamped on every claim: say whether a number was measured (by whom, on what card), read in the code (where), or inferred (and what would test it). The drift card holds one of each kind left open: its cause, the card's clocks, is inferred, and nobody has measured them.
