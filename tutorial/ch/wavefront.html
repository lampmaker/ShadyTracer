Wavefront path tracing

The plain way to put a path tracer on a GPU is one kernel, one thread a path, looping over bounces until the path ends. ShadyTracer does not do that. It splits a path into small steps done by small kernels, each run over every ray that needs that step, the rays passed between them on queues in the card's memory: a wavefront. This chapter is one sample run that way, iteration by iteration, the queues and the counts that size each dispatch, and what the split buys and costs.

1A sample, iteration by iteration

The sunlit room of chapter 20, without its dust, its walls paler so paths go round it: 64 pixels, 16 paths each, 1024 paths in one sample. Every path starts in the first iteration's queue. Each iteration runs the same few kernels in turn: the march moves every waiting ray up to 32 steps; shade handles the rays that reached a surface or left the room, queues a shadow ray towards the sun and puts each path's next leg in the next iteration's queue; occlusion traces the shadow rays queued the iteration before. Point at the bars for each iteration's counts. In the first, all 1024 rays marched, 812 reached something, and 212 were still on their way after 32 steps.

Paths end at different times: at the sky, at the bounce cap (10 here, ShadyTracer's default), or out of steps. So the queues drain. Iterations 12 to 19 carry fewer and fewer rays, and 20 to 24 none at all, but each is still dispatched: the card is told to run zero workgroups, which costs little but not nothing. How many iterations to run is decided before the sample starts, because the program on the main processor does not wait to read the counts back: ShadyTracer runs the worst case, one iteration a bounce plus one for every 32 steps a path may take, (10 + 1) + 400 / 32 rounded up = 24.

With 8 iterations, paths still going at the last are cut. A ray still marching on the last pass is flushed: it ends there and hands in the light it has gathered, 88 of them here. A path shaded on the last pass has its next leg written for a march that never comes: 775 cut. The picture's mean falls from 0.0153 to 0.0145.

With 4 it reads 0.0106: nearly a third of the light gone, as a low bounce cap loses it (chapter 13). ShadyTracer's budget is always the worst case, and at the worst case no path runs out of iterations: a path's legs each end part-way through a pass of 32 steps, so it needs at most one pass a leg plus its steps over 32, and one that would need more steps than maxiter ends anyway. Drag the slider to see where the picture stops changing.

2Queues in the card's memory

Inside one iteration. The rays wait in one of two ray buffers; the march reads one and writes the other, and the next iteration the two swap, so no ray is read and written in the same place at once (a ping-pong). A ray that reaches something is written to the shade queue instead. Each write takes the next free place by an atomic add on the buffer's count, so a thousand threads writing at once never take the same place.

Before each kernel runs a tiny one, one thread: it reads the count of rays waiting and writes how many workgroups the next kernel needs, into a buffer the card reads the next dispatch's size from (an indirect dispatch). The program on the main processor never learns the counts while the sample runs; it records the whole chain once and the card sizes every step itself.

Surface and shade run over the shade queue. Shade writes each path's next leg after the march's survivors in the buffer being written, and each shadow ray to the write side of the shadow queue, which takes turns the same way.

The flip, one thread: the buffers swap roles, and the counts of the side the next iteration will write are cleared. Press Next kernel to step through.

In iteration 2, occlusion traces the 523 shadow rays shade queued in iteration 1. Shadow rays march too, 32 steps a round: on the last pass, the occlusion runs again, round after round, until every one has ended, because one counted while still marching would be counted unblocked.

Iteration 15: 56 rays marched, a few workgroups out of what the card could run at once, each step of every kernel still paid for.

3Why split a path

Chapter 21's lanes again, for the whole sample. Written as one big kernel, a thread a path, a group of 32 paths marches each leg as long as its slowest path's leg, shades whenever any of its paths has something to shade, and keeps going until its longest path ends, the finished lanes waiting. As a wavefront, each kernel runs over a queue of rays that all need that step, packed into full groups. Time is counted in lane steps, a shading costing what you set (here 20 march steps; that is a model's number, not a measurement): the big kernel's lanes are busy 46% of the time, the wavefront's 74%, and the big kernel takes 1.6 times as long.

If shading cost no more than a step, the wavefront still wins (61% against 33% busy): most of the big kernel's waste is paths of different lengths kept together to the end.

The dearer the shading, the more both are shading, and the closer they come (86% against 64%). This is the argument Samuli Laine, Tero Karras and Timo Aila made for this way of working (2013). ShadyTracer's code gives reasons of its own as well: a kernel that only marches need not compile the shading code (the march kernel's comment), and each kernel needs only the buffers its step uses, under the eight a kernel may have (chapter 21).
