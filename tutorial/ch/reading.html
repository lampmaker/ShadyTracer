How to read this

What the parts of every chapter are for, how to read a figure, a stamp and a piece of code, and how to run ShadyTracer and its tests yourself, so that you can check what the chapters say against the real thing.

1What this tutorial is

ShadyTracer is a renderer: a program that makes pictures of 3D scenes, in a web browser, on the graphics card. This tutorial explains how it works inside, from the first ray to every trick that makes it fast, for someone who wants to understand its code, build a renderer of their own, or improve this one. It sits beside the program and is not part of it.

It is not a manual. How to use ShadyTracer (build a scene, light it, render it) is in the program's own Help: press F1, or open Help › Contents.

Every chapter has the same parts, in the same order:

  1. The question, in a line and a picture.
  2. The idea, in plain words beside a live figure. Paragraphs with a dot beside them move the figure when you scroll to them, or click them.
  3. The maths, folded away in a box. Every chapter reads without it: open it when you want the real equation, with every letter named.
  4. How ShadyTracer does it: pieces of its real code.
  5. Tricks and trade-offs, each stamped with how sure it is (section 5).
  6. What went wrong before: the bugs the code's own comments tell, and why the code looks the way it does because of them.
  7. Try it: things to do in the figures, and in ShadyTracer.
  8. Words from this chapter, and boxes with where to read more: the books and articles the ideas come from.
The mathsWhat a fold-out looks like

Like this: the equation, then each part of it named. For example, the brightness a lamp gives a surface straight in front of it, r away, in 3D:

E = Ir2

E
the light arriving on each bit of the surface (its irradiance)
I
how strongly the lamp shines (its intensity)
r
the distance; why it is squared is the next section

2Reading a figure

The figures are drawn and computed in your browser while you read: each one is a small renderer of its own, written to follow ShadyTracer's rules, and where ShadyTracer has a piece of JavaScript that does the job (a shape, a blend, a random number generator, a lens), the figure runs that very code.

Within a style, the same colour and line mean the same thing in every figure. This is the key, drawn in the style you are reading in. A circled cross (⊕) is a handle: drag it with the mouse or a finger, or click it and use the arrow keys. A figure that is three-dimensional turns when you drag its background.

Below each figure: its controls (sliders, switches), and a line of text, its readout, that says in numbers what the figure is showing now. When a paragraph says "the readout", it means that line.

3The flat world

Most figures show a slice of a scene, seen from the side: a flat world. A slice can be drawn whole, and its shapes dragged. The ideas are the same as in ShadyTracer's 3D scenes, but a few numbers are not, and this figure shows why. A lamp sends its light out in every direction. In the flat world it spreads around a circle; in 3D, over a sphere.

Drag the handle out to twice the distance. The circle is twice as long, so the same piece of surface catches half the rays: the light falls as 1/r. A sphere twice as far has four times the area, so in 3D the same piece gets a quarter: 1/r². The flat world's light weakens more slowly than the real world's.

The same happens to every law with a direction in it. A matte surface sends its light back over a half-circle in the flat world and over a half-sphere in 3D, so its numbers differ too (½ in one, 1/π in the other: chapter 8). Wherever a formula changes between flat and 3D, the page says so, and the figures that need the real laws are 3D.

4Reading the code

Code is never copied into a page. Each piece is named (a file and a function, or a line it starts with), and your browser reads it from ShadyTracer's own files when the page opens, so it is the code as it is today. Above it: the file and its lines (a link to them on GitHub), the language, and a line of plain words saying what to look for. Here is one, from the file that holds ShadyTracer's version number:


    
ShadyTracer's code is in two languages. The parts that run on the main processor are JavaScript. The parts the
      graphics card runs are kernels written in WGSL, which sit inside the
      JavaScript files as long pieces of text. A label above each piece says which it is.

    
A short reference to a line, such as
      , is a file name and a line number: follow it
      to see that line. Each piece of code was checked against the words around it when the page was written. If the
      code has changed since, the page says so above the piece ("changed since this page was checked"), and the words
      may no longer fit.

    
The comments in ShadyTracer's code are long, and they matter: they say why the code is written as it is,
      often by telling what went wrong before. The chapters quote them, and say so when a comment has gone out of date.

  






  

    
5How sure is each claim?

    
The people who write ShadyTracer hold every statement to one question: do I know this, or do I
      think it? Wherever it matters, the chapters say which, with a stamp. Point at a stamp to see its card.

    

      
Measured: someone ran it on a real graphics card and wrote the number down. The page says who,
        on which card, the number, and where it is recorded. Chapter 14's cost of shadow rays is one.

    

    

      
Read in code: the code does this, and the page links the line. It says what the code
        does, never what it costs: how long something takes is only ever measured.

    

    

      
Inferred: a reasonable guess, not yet tested, written as a guess. The page says what would test
        it.

    

    
Why not measure speed on any computer? Because ShadyTracer's speed is the graphics card's, and a computer without
      one can only imitate it, slowly and differently. So every number about speed comes from someone's own card. They
      open ShadyTracer, choose View › Tests and press a test's button; a table of results appears
      with a Copy button, and that table is pasted back into the project's notes. Its first line names
      the exact code it ran, because the test bench writes it there:

    

    
The tests themselves are rows in one file, lib/pathtracer/tests.js, so a new measurement is a new
      row, not a new program (docs/TESTING.md
      says why).

  






  

    
6Running ShadyTracer

    
The quickest way is the published copy: open lampmaker.github.io/ShadyTracer
      in a browser with WebGPU. To run your own copy, and read and change its code:

    
git clone --recursive https://github.com/lampmaker/ShadyTracer.git
cd ShadyTracer
python3 -m http.server 8000

    
and open http://localhost:8000/. What it needs:

    
    
      
  • A browser with WebGPU: Chrome or Edge 113 or later, Firefox 141 or later on Windows, or
        Safari 26 or later.
    • 
      
  • A real graphics card. The results in these chapters were measured on NVIDIA cards.
    • 
      
  • A web server, even the one-line one above: opened straight from the disk
        (file://), the page does not work, because WebGPU needs a secure context and
        localhost counts as one (ShadyTracer's README). This tutorial is served the same way:
        http://localhost:8000/tutorial/.
    • 
      
  • --recursive: two of the libraries it needs are separate repositories inside it.
        In a copy made without it, git submodule update --init fetches them.
    • 
    

    
Nothing is built or installed: the files in the repository are the program. If a scene you made stops the program
      from starting, add ?safe to the address: it starts without compiling your scene (and does so by
      itself after a start that never finished).

  






  

    
7Running the tests

    
Most of what can be checked without a graphics card is, by small programs run with node. They come
      in three kinds, by the end of their name:

    
    
      
  • *.test.mjs: plain checks, no graphics card. Every pull request runs all of them on GitHub, and so
        should you before you change anything: the list is in CLAUDE.md, and the check on GitHub reads it
        from there ().
    • 
      
  • *.gpu.mjs: run the real kernels on a graphics card simulated in software (they need the
        webgpu package for node). Slow, and a check of correctness, never of speed.
    • 
      
  • *.check.mjs: open pages in a browser with no window (they need Playwright).
    • 
    

    
And one more, to run before every change: node lib/pathtracer/core/check-shaders.mjs. It loads every
      kernel against every example scene and checks what a browser would otherwise only find when the page fails to
      start. Its first comment says why it exists:

    

    
This tutorial has its own checks: node tutorial/test/tutorial.test.mjs (run on GitHub with the
      others) holds every page, link, glossary word and piece of code to today's files and tests the figures' renderers
      against answers worked out by hand; node tutorial/test/pages.check.mjs opens every page in every
      style. And node tutorial/review/affected.mjs lists the chapters a change to ShadyTracer touches, so
      the tutorial is read again whenever the code it explains changes.

8Try it

    
    
      
  • In the flat world figure, put the circle at 1.0 and then at 2.0. Count the bold rays that reach the piece each
        time (the readout counts them too).
    • 
      
  • Open ShadyTracer, press F1, and find the page on signed distance functions. Then read chapter 2 here: the
        Help says how to use them, the chapter how they work.
    • 
      
  • In your own copy, run node lib/pathtracer/core/check-shaders.mjs. Then put a backtick in a
        comment inside a kernel, run it again, and see what it says. Take the backtick out.
